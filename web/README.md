# web/ - React + TypeScript + Vite front end

Everything on the form is generated from the engine's schema (`GET /api/classes/{id}/schema`): groups become sections, `type`/`unit`/`options`
pick the widget, `applicable` hides fields for the selected content type, `computed` fields are read-only (values come from the result's
`derived`).  Per-content-type values are kept separately (like the workbook's columns): switching content type loads that content type's
defaults the first time and remembers edits afterwards; level and companion level are shared; "Copy stats from" copies between visited
content types.  Any change triggers a debounced (350 ms) `POST .../compute`; 422 field messages are shown under the fields and in a banner.

## Commands

```bash
npm install
npm run dev            # http://localhost:5173, talks to VITE_API_URL (default http://localhost:8000)
npm run dev:mock       # same UI, no backend: VITE_MOCK=1 serves the fixtures (result numbers scale with Flat ATTACK)
npm run build          # tsc --noEmit + vite build -> dist/
npm test               # vitest: formatter, schema->form logic (iterates every class fixture; a class without a map entry in xlsx_map.json is an engine-native one with no Excel calculator), class picker, profiles, render smoke tests, mock API
```

`.env.example` lists the env variables (`VITE_API_URL`, `VITE_MOCK` and the four optional `VITE_FIREBASE_*` of the accounts feature).  The API must allow the dev origin (its default CORS list already has
`http://localhost:5173`; set `MSI_CORS_ORIGINS` in production).

## Theme (Auto / Light / Dark) and the Help tab

* **Theme button** (header, right of the class picker) cycles **Auto** (follow the system) -> **Light** -> **Dark**.  The choice is stored in `localStorage` (`msi.theme`; Auto removes the key; blocked storage just
  means the choice is not remembered) and applied as `data-theme="light|dark"` on `<html>` (absent = Auto) plus `color-scheme`, so native controls and scrollbars match.  A tiny inline script in `index.html` applies the
  saved choice before the first paint (no flash); keep its key in sync with `THEME_KEY` in `lib/theme.ts`.  The palette is **one set of CSS variables** in `styles.css`, each written once as
  `light-dark(<light>, <dark>)` and resolved by `color-scheme` (Auto = `light dark`, i.e. the OS; `:root[data-theme="dark"|"light"]` force it).  Never hard-code a colour outside that block (a test fails if one
  appears in `styles.css` or a component sheet).  `light-dark()` needs a 2024+ browser; older ones get the light palette through an `@supports not` fallback and the toggle has no visible effect there.
* **Help tab** (last tab): how to use the app, which stats to type (the selected class's schema `help` texts per field), the modelling conventions (baked-in artifacts, time-weighted blending, the second-by-second schedule,
  companion summon rules, how to read "units per +1% DPS"), a per-class "what is modelled" table (from `classes.json` / `status`: Calculator, Artifacts, Companions, Stat values, Cubes, Equipment compare) and at most
  12 "Known limitations" bullets condensed from `KNOWN_GAPS.md` with a link to the full file on GitHub.  Edit the wording in `src/content/help.tsx`; the claims there mirror `APP.md` / `KNOWN_GAPS.md` and are not
  generated, so re-read them when the engine's conventions change.

## Classes, hints and the companion section

* The picker lists every class of `GET /api/classes` (the first 12 workbook-verified, the Cygnus classes engine-native) grouped by job family (Warrior / Mage / Archer / Thief / Pirate) with the stat identity, and a Status line for the
  selected class: Companions (yes), Artifacts (yes for the classes whose schema says `artifacts_modelled`: today every class), Stat values (yes for every class with `status.stat_values`: today every class; a class without it reads "coming soon").  The data comes from
  `GET /api/classes` (`family`, `status`); the form itself needs nothing class-specific, it is generated from each class's schema (Flat STR / DEX / LUK / INT,
  Defense %, Incoming Hit Rate ... appear when the schema has them).
* Numeric fields carry the schema's `min` / `max`: HTML `min` / `max` attributes (the inputs are `type=text` so "1,209,199" and "1e6" can be typed, which
  means the browser itself does not enforce them), an immediate inline range message that holds back the request, and a "(0 - 100)" hint after the schema's
  `help` text.  The API re-checks the same bounds (422).
* "Companion" section (a presentation grouping, the schema keeps its own groups; Status Effect Damage is a damage modifier and sits in "Damage modifiers") keeps only: the **Companion** dropdown ("None (no companion)" + the companions you own on the
  Companions tab; with none owned just "None" and a "Set up your companions" link), a read-only **Companion level** line ("Shadower: level 7 (set on the Companions tab)" + "Edit companions", which
  switches tab), Companion Summoning Time Increase % and Status Effect Damage (stats, so they stay).  The schema's `companion_level` field is no longer an input: `buildInputs` fills it with the level of
  the chosen companion from the Companions tab (a companion that is not owned is sent as "None" / level 0), so the API contract is unchanged.  With no companion the result never says
  "Companion: None"; classes with a player stun (Hero's Rush) show it as "Stun effect (no companion)".
* **"Equipped artifacts" section** (`components/EquippedArtifacts.tsx`; after "Additional bonuses", just before "Companion"; nothing for classes without artifact support): `schema.artifacts.max_slots` (5) slot
  dropdowns ("(none)" + the 36 artifact names), the workbook's "Equipped Artifacts" Slot rows.  The choice is a **per-content-type input** like the stats above it: it changes with the content type dropdown, is
  saved per content type in the profile (`FormState.equippedArtifacts`: content type -> `max_slots` ids, "" = empty slot) and is what the compute request's `artifacts` list (and the Sensitivity / Stat values
  request) holds.  An artifact fits ONE slot (it is disabled in the other slots; `setSlot` refuses a duplicate and `normalizeSlots` drops repeats at load).  A content type visited for the first time starts with empty
  slots (like its other values it starts from the defaults, nothing is copied from the previous content type); "Copy stats from" copies the slots too.  Each filled slot shows the artifact's star (set on the
  Artifacts tab, shared by every content type) and a link to that tab.

## Companions tab

The full companion input page (the workbook's `CompanionsInput` sheet); state in `FormState.companions = {levels: {name: 1..18}, potentialLinesPct}` (absent name = Not unlocked), saved with profiles
(localStorage + JSON export / import) and repaired on load.  **Old profiles** (no `companions`) are migrated by `normalizeState`: every companion chosen in any content type stays owned at the old shared
`companion_level` (level 0 = nothing was owned, the choice becomes None).  Choosing a companion on the Calculator, the "use in <content type>" / "use none" links of this page, the "chosen" marker and
profile load / import all read and write the same state.

* **Your companions** table (the 16 companions, schema order, "Sort by rank" checkbox): level selector Not unlocked / 1..18, the resolved level, **DPS gain vs no companion**, **% of Total DPS (without a
  companion)** and **rank** (among the owned ones, from the Sensitivity `companions` part; "n/a" for classes without stat values, with the text "gain: not available for this class yet"), a "chosen" chip on the
  companion of the current content type, a "best for <content type>" chip + highlighted row on rank 1 and a sentence comparing the best with the chosen one.  Numbers are shown only for a row that was
  computed at the level now selected (a changed level shows "..." until the new answer arrives).
* **Summoning Time Increase potential lines**: the workbook's table - every total that 1-3 boots lines can add up to (5 ... 60, lines roll at the item's tier or the one below; the combinations are a port of
  `companion_model.potential_line_totals`, tested against the engine's totals), with the window, DPS gain / % gain vs none of these lines, DPS vs your current setup and, in Breakthrough / Hero Dungeon, the
  boss-phase columns (average DPS change, time factor, total damage).  The one input is "Lines already counted in your Summoning Time Increase %" (`companion_potential_lines_pct`: the part of the
  Calculator's value that comes from re-rollable boots lines, default 0; the Cubes tab's lines of that stat can be copied with one click); the row equal to it is marked "yours".  Rows where the table itself shows a jump
  (slope more than twice the median) get a "step" chip, and the explanation text covers the thresholds (e.g. Blaze Wizard's 3rd stun cast needs +13.667%, so +13% gains almost nothing over +12% and +15% a lot).
* **Requests**: `POST .../sensitivity` with the compute inputs + `companion_levels` (all 16, 0 = not unlocked) + `companion_potential_lines_pct` + `which: ["companions"]` (+ `"summon_time"` once a companion is
  chosen), only while the tab is visible, 600 ms debounce, aborted when superseded (the same `useSensitivity` loader as Stat values; the component stays mounted).  Classes without stat values never call the API.
* **Mock mode**: the class's sensitivity fixture (already holds both parts) is re-labelled with the requested levels (`relevel`: owned ones ranked by the fixture's gains, the numbers are the fixture's).

## Artifacts tab

Capability comes from the class's schema, never from a class list: `schema.artifacts_modelled` + `schema.artifacts` (`artifactsAvailable`; the class list's
`status.artifacts` is only a fallback while no schema is loaded).  Classes without it get a friendly "Artifacts are not available for <class> yet" panel and
`artifacts` is never sent with their compute request (`buildInputs`); a class that gains artifact support in the engine shows the tab with no web change.

* **One table** (`components/ArtifactTable.tsx`, like the workbook's `ArtifactsInput` sheet): all 36 artifacts as rows in the workbook's order (grouped Epic / Unique / Legendary, the schema's order), edited
  directly on the row.  Columns: **Artifact** (name, rank, the badges below, a small effect text at the chosen star), **Star level** (dropdown "Not unlocked", Star 0 .. Star 5 (max); the tooltip says
  "Not unlocked acts as star 0 when the artifact is equipped"), **Equipped** (read-only: an "equipped" marker for the artifacts equipped in the CURRENT content type, the choice is made in the Inputs tab's "Equipped artifacts" section, linked from the intro note), **Line 1 / 2 / 3** (rarity + stat dropdowns, the line's value, "= N DPS" and "(locked: star n)" until the star
  unlocks it; line 3 exists only for Legendary artifacts, the others show a dash: `lineCount` = the engine's rule, tested against the cube meta) and **Potential total** (the artifact's potential gain, % and DPS).
  The header is sticky inside the table's own scroll box (`max-height: 75vh`, scrolls both ways, so it also works on narrow screens); above it a "filter by name" box, "Show only unlocked / equipped"
  (unlocked = a star level is set or it is equipped in the current content type) and "n / 5 equipped in <content type>".  At most `schema.artifacts.max_slots` (5) artifacts can be equipped per content type
  (the slot dropdowns; an artifact once).
* **State** = `FormState.artifacts: Record<artifact id, {star: 0..5 | null, lines: [{rarity, stat} x 3]}>` for all 36 artifacts (null = Not unlocked; a new table starts at the workbook's default star by
  rank - Epic 5, Unique 3, Legendary Not unlocked - no lines; stars and lines are shared by every content type) and `FormState.equippedArtifacts: Record<content type, string[max_slots]>` (the Inputs tab's slots, see above).
  Saved with profiles (localStorage + JSON export/import, export `version` 2).  `normalizeState` (`normalizeArtifacts`, `normalizeEquipped`) repairs junk (unknown artifacts dropped, missing rows defaulted, bad stars -> default,
  lines padded, repeats / unknown ids in the slots emptied, at most 5 slots) and **migrates profiles saved when equipping was ONE global `equipped` flag per artifact**: when `equippedArtifacts` is absent EVERY content type of the schema starts
  from that old equipped set (schema order, capped at 5), once - after that the per-content values are the truth and the flags are gone from the in-memory shape (a profile with `equippedArtifacts` is never re-seeded).
  It also **migrates profiles saved before the table** (a slots LIST `[{key, star}]` + the separate `potentials`
  state of the old "Artifact potentials" section): equipped = the slots with their star, the old potential entries give the lines and own stars, everything else the default; the old fields are dropped on the
  next save.  The engine request is `inputs.artifacts = [{key, star}]` for the CURRENT content type's slots only, in the schema's order (stable), "Not Unlocked" for a null star, at most 5 (the API contract is unchanged).
* **Potential gains**: `POST .../artifact-potentials` (the same lazy, debounced `useLive` request as before: only while the tab is open, only when some line is set, aborted when superseded) with an entry
  per artifact that has a line (`potentialsRequest`: its table star, its lines; a stat / rarity the tables do not know - from an old profile or an import - is sent as "(none)" because the API would refuse the
  request, and is flagged in the row).  Classes without stat values show the table without gains and the note "Artifact potentials are not available for this class yet."; the lines can still be edited and
  are saved.  The stat / rarity dropdowns come from `GET .../cubes/meta` `artifact_potentials` when loaded, else from the app's static copy (`lib/artifact_potential_tables.json`, equal to the meta: a test checks it).
  A stored stat that artifacts cannot roll stays selectable as ONE option "<stat> (not rollable on artifacts)" with a warning icon / title and is never offered otherwise.
* **Effect text** per equipped artifact is the engine's star value at the chosen star (`lib/artifact_values.json`) in the wording of `EFFECTS` (`lib/artifacts.ts`, one
  entry per artifact with `{value_key}` placeholders; tests check every artifact of the schema has an entry and every placeholder exists in the value table).
* **Badges**: "Baked into your stats - type the stat into Inputs" (Book of Ancient, Athena Pierce's Old Gloves, Clear Spring Water, Soul Pouch, Lit Lamp, Star Rock, Cursed
  Doll, Shamaness Marble; "Partly baked" for Bottle of Emotion's Final Damage and Reindeer's Spear's base Defense Penetration, whose Attack % / extra boss+PvP applications
  are live), "Companion effect" (Arwen's Glass Shoes, Hexagon Necklace, Charm of the Undead, Horn Flute; clicking jumps to the "Companion" section on the Calculator
  tab), "No DPS effect" with the engine's reason (the 7 flagged artifacts, greyed).
* **After a compute**: "What the equipped artifacts do in this calculation" lists, per equipped artifact, the value the engine used (`result.artifacts.rows` /
  `reference_only`, the latter marked "reference only") and the bucket it feeds, plus the non-zero bucket totals.  A second compute without artifacts (only while the tab is
  open and something is equipped, debounced 500 ms) gives the labelled "Total DPS with these artifacts vs. none" delta.
* **Equip ranking** (all 36 artifacts, best first) embeds `EquipRanking` (the Stat values tab's table) fed by `POST .../sensitivity` with `which=["artifacts"]`
  (`useSensitivity`, only while the tab is open); classes whose `status.stat_values` is false show "not available for this class yet" instead.  The request carries `artifact_stars` = the table's star of EVERY
  artifact (also the Stat values tab's artifacts part, via `App`), so an unequipped artifact is ranked at the star you set in its row; the what-if "equip" adds the artifact to what you have equipped even when
  all 5 slots are used (the engine's equip toggle is not capped).
* **Mock mode**: `<id>.artifacts_case.json` (real engine output for Alliance Badge 4, Arwen's Glass Shoes 2, Book of Ancient 5, Pig's Ribbon Not Unlocked) is returned when
  exactly those slots are requested (in any order); any other slot set returns the plain fixture result plus an artifacts block that only lists the equipped artifacts.

## Stat values tab

`POST /api/classes/{id}/sensitivity` (see `api/README.md`) drives the tab; it requests only while the tab is visible (the component stays mounted, so tables survive a tab switch), 600 ms
after the inputs stopped changing (a call costs ~0.5 s), and aborts the in-flight request when the inputs / class / requested parts change or the tab is left.  The previous tables stay
on screen dimmed (with a spinner) while the new ones load; the first load shows a spinner + skeleton.  `which` is used lazily: `stats` first, then `artifacts` (right after the stats
are in), and `companions` / `summon_time` / `cdr` only once their collapsible section is opened.  Only parts that are missing for the current inputs are asked for.

* **Stat table** (the 27 stats): rank, stat (+ its semantic note, e.g. "adds the main stat's flat-Attack channel"), current value, new value with the step ("+1", "+1 pp", "+1 lvl", "x1.01", "+1 (DR 150)"),
  **Units per +1% DPS** (units of the stat that give +1% total DPS = 1 / (% gain of one step - 100); LOWER = fewer units needed = each unit is worth more; n/a = one step gives no gain),
  DPS gain and % gain of one step, a relative-value bar (gain of one step relative to the best stat), and notes: the step text plus "timing re-run" (this stat's block re-solved the Status /
  KO timeline instead of reusing the baseline one) and "summon time re-searched" chips, flagged only when other rows show the opposite; the row tooltip spells out `strip_reused` /
  `summon_time_pinned`.  Sort: best value first (default; n/a rows last), workbook order, name.  Note that "units" are per stat unit, so +1 Flat INT and +1 percentage point are not
  comparable one to one - compare the DPS / % gain per step or the units to what a unit costs you in game.
* **Equip ranking** (`components/EquipRanking.tsx`, `<EquipRanking rows={result.artifacts.rows} limit? showLocked? showNoEffect? title? />`, self-contained, used by the Artifacts tab too):
  unlocked artifacts with an effect by `rank_position`, then unlocked "no DPS effect" artifacts greyed with the engine's reason, then locked ones greyed ("what-if at star 0, unranked");
  equipped ones are marked (their gain is what removing them would cost; same % either direction), "in Inputs" marks baked-into-Inputs artifacts (the gain is a what-if on top of
  the typed stats).
* **Collapsible sections**: Companion comparison (16 companions at the chosen level: gain / % / rank, chosen one marked), Companion summoning time potential, Cooldown decrease milestones.
* **States**: 501 (or `status.stat_values` false) -> "Stat values are not available for this class yet." without calling the API; 422 -> the field messages; 429 / 504 / network -> message
  + "Try again".
* **Mock mode** serves `<id>.sensitivity.json` / `<id>.sensitivity_meta.json` for every stat-values class (real engine output for the sample case, filtered by `which`; the numbers do not follow your edits);
  the other classes answer the same 501 as the API.

## Cubes, Equipment compare and artifact potentials

Three views over `GET .../cubes/meta` + `POST .../cubes | equipment-compare | artifact-potentials` (see `api/README.md`).  They exist for the classes whose `status.stat_values` is true (the stat prices come from
the stat-values engine (every class today); for a class without it each shows "... is not available for this class yet" without calling the API (and a 501 from the API gives the same text).  The static tables
(`useCubesMeta`) are fetched once per class, the first time one of the three is opened.  All three keep their data in the profile (`FormState.cubes / equipment`, and the artifact potential lines inside `FormState.artifacts`; saved with localStorage profiles and the
JSON export/import, repaired on load, absent in older profiles).

* **Cubes tab** (stays mounted, so a result survives a tab switch).  The editor is the PotentialCubes sheet: 15 slots x {Potential, Bonus Potential}, each with rarity, pity count (the cap of that rarity on that
  track is shown next to it and bounds the input: the two tracks have different caps) and 3 lines (stat dropdown: ONLY the stats that piece of equipment can roll, `stats_by_slot` of the meta - Potential and Bonus Potential share the list, the engine's roll tables are keyed by slot and rarity, not by track; a stored stat outside it, e.g. from an old profile or an Excel import, stays selectable as one flagged option "<stat> (not rollable on this slot)" with a warning icon and title; plus a value).  Nothing is requested while you
  type.  **Calculate** sends the rows you filled in (or, with the checkbox, all 30; blank = Normal with no lines) 6 rows at a time (`CUBES_CHUNK_ROWS`: 5 requests for the whole sheet, under the API's 20 per minute),
  each request carries the whole gear (summoning-time lines of other rows matter) plus `only`; a progress bar counts rows, **Cancel** aborts the request in flight and keeps what arrived, a failing chunk (429 / 504 / 422 /
  network) stops the run with a message and keeps earlier rows, 501 shows the "not available" text.  The ranking updates as rows arrive and says "outdated" when the inputs or the gear changed since.  Columns: slot / track,
  current rarity + pity + lines, what they are worth now (% of Total DPS), cubes to a positive EV (`smallest_n`; "never"), N for a 50% / 75% chance that some reroll beats them (`> 1000` = not reached), expected gain at the
  selected cube count (5 / 20 / 50 / 100 / 200 / 500 / 1000; % and DPS), and **Worth rolling?**.  Rank by: best expected gain at the chosen cubes (default), fewest cubes to a positive gain, or sheet order.  **Download CSV**
  writes the script's 57 columns (24 milestones).  Text on the page explains Potential vs Bonus Potential pity caps (from the meta, 30/60/120/333/714 vs 42/75/150/417/714) and the crit-rate-cap note.
  *The "worth rolling?" rule* (`worthRolling` in `lib/cubes.ts`, for the selected cube budget N): `smallest_n` null -> **No** (no cube count up to 1000 has a positive expected gain: at or near the best the slot can roll);
  EV% at N >= 1% of Total DPS -> **Yes**; >= 0.1% -> **Maybe**; otherwise **Marginal**.  The EV already assumes optimal stopping (you only keep better rolls), so it is never negative; the rule does not know what a cube costs
  you - it ranks, you decide (thresholds are the exported `WORTH_YES_PCT` / `WORTH_MAYBE_PCT`).
* **Equipment compare tab**: two editors (fixed Attack line + 5 lines: stat dropdown of the 21 stats + value) for the current and the new equip.  Live: 500 ms after you stop typing (`useLive`; the call is cheap once the
  server has cached the character's stat prices, the first one costs ~1 s), previous answer dimmed meanwhile.  Shows each equip's gain (% of Total DPS and DPS, per line; a second line of the same stat is marked as merged
  into the first), the delta of new vs current ("+x% of Total DPS" and a sentence), and a note when Critical Rate is priced as Critical Damage (live crit rate >= 100% without Ring of Cycles / Book of Ancient).
* **Artifact potentials** are part of the Artifacts tab's table now (see "Artifacts tab"): the lines of every artifact (rarity + stat, only stats artifacts can roll, a stored other stat flagged like above) with the
  per-line gain and the artifact's total (same-stat lines add, different stats multiply), live like the equipment compare; a reference calculator that does not change the main result.  The Equipment compare
  editor's own 21-stat list is unchanged.
* **Mock mode**: `<id>.cubes_meta.json` (real meta), `<id>.cubes_case.json` (real engine rows for a sample gear: the rows are the fixture's whatever you type, labelled with your gear and a mock note),
  `<id>.equipment_case.json` and `<id>.potentials_case.json` (real answers + the DPS-per-unit tables, so edits to equipment / potential lines ARE recomputed in the browser with a TypeScript port of the engine formula, which the
  tests check against the real engine output).  Classes without these fixtures answer the API's 501.

## Accounts (Google sign-in, optional)

Design: `APP_ACCOUNTS_DESIGN.md` (repository root).  Signed-out use is unchanged (profiles in `localStorage`); with an account the profiles (and the theme + last class) can follow the player to other browsers.

**Switch.**  The feature exists only when all four **`VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, `VITE_FIREBASE_APP_ID`** are set at **build** time (public web-app identifiers from the Firebase
console, not secrets; put them in `web/.env.production` or the environment of `deploy/deploy_web.sh`; local development: `web/.env.local`).  With any of them missing the build is the app without accounts: no sign-in button,
no account code in `dist/` (the lazy chunk is not even emitted) and no Firebase code.  Console steps and deployment: `deploy/README.md` ("Accounts setup").

**What loads when.**  The main bundle only gains a few hundred bytes (the flag, the tiny `lib/cloud/bridge.ts`, the cloud icon).  With the flag on, the account UI is one lazy chunk (`AccountRoot`, ~43 kB / 15 kB gzip + 4 kB css) fetched at
start-up (it holds the sign-in button).  The **Firebase SDK is a further, separate set of chunks (~290 kB / ~88 kB gzip: `firebase/app`, `firebase/auth`, `firebase/firestore/lite`)** that is only downloaded when the pointer / keyboard focus
reaches "Sign in with Google" (so the popup can open inside the click), when it is clicked, or when a previous session is restored (a `localStorage` flag `msi.cloud.session.v1`).  A visitor who never signs in never downloads it.
`Firestore Lite` is used on purpose: the design needs only `getDocs`/`getDoc` + batched writes (no realtime listeners, no offline cache), and it is ~5x smaller than the full SDK.

**Data and rules.**  `users/{uid}`, `users/{uid}/profiles/{profileId}` `{classId, name, updatedAt, deleted?, state}`, `users/{uid}/settings/app` `{theme, lastClassId, lastProfileId?, updatedAt}`; rules `deploy/firebase/firestore.rules`.
`state` is the profile's `FormState` as a canonical JSON **string** (opaque to the cloud code: it is only stringified, hashed and passed through `lib/profiles.ts`' own `parseImport` normalisation, so form-state changes need no cloud change; a string
also avoids Firestore's nested-array / `undefined` restrictions and per-field indexing).  Limits: 50 profiles per account (client-side), `state` <= 180,000 characters, name <= 80, ids `[A-Za-z0-9_-]{1,64}`.

**Behaviour** (all pure logic in `lib/cloud/merge.ts`, tested exhaustively):
* Local-first.  Edits only touch `localStorage`; the cloud is written **only** by **Save to account** (account menu or the Profiles tab): one batched commit with the profiles whose content differs from the baseline (the hash of the version last seen
  in the cloud), the pending deletions as tombstones (`deleted: true`, content emptied), the expired tombstones deleted (client sweep, 30 days), the settings if they changed, and `users/{uid}` (`lastSeenAt`).  No pre-read: it is last-write-wins at
  document level, so use **Refresh** first after working on another device.
* Reads: one `getDocs` of the profiles (one read per document, tombstones included) + one `getDoc` of the settings, only at sign-in and on **Refresh from account**.  No listeners anywhere.  Offline persistence of the SDK is not enabled (the dirty state
  is persisted by the app, a failed save is simply retried: automatically once when the browser comes back online, plus the Save button; transient errors are also retried 3x with back-off).
* Merge by `profileId`, newest `updatedAt` wins (tie: the cloud).  Edited on one side only: that side wins (cloud change = "updated from another device" notice).  Edited on both: newer wins and the **losing version is kept in the local history**
  (`msi.cloud.history.v1`, 20 entries / 1.5 MB; account menu > Version history > Restore as new profile).  Delete vs edit: a newer edit wins over a delete; an unchanged copy is removed (copy to history).
* First sign-in on a browser that has profiles: dialog "Upload your N local profiles?" (all / choose / not now).  "Not now" marks them **local only** (never counted as unsaved); the menu offers "Upload local-only profiles...".
* Sync metadata per account: `msi.cloud.meta.v1.<uid>` (baselines, pending deletes, skipped ids).  Use one tab at a time (two tabs would overwrite each other's metadata).
* Unsaved changes: a dot on the avatar, an "unsaved" cloud icon per profile (Profiles tab: synced / unsaved / local only / error), and a `beforeunload` warning.  A profile that is over the size limit or beyond the 50-profile cap stays unsaved with an
  error line (never silently dropped).
* Sign out: choose to keep or clear this browser's profiles.  **Download all my data (JSON)**; **Delete my account and data** (type DELETE, Google re-authentication first, then all documents, then the Auth user).
* The privacy note (what / where / how to delete, link to Help > Accounts) is shown before the first Google sign-in.

**Tests** (`npm test`): `lib/cloud/*.test.ts` (merge, store against an in-memory fake Firestore SDK with read / write counters and no listener API, controller flows, auth popup/redirect/delete order, ports, rules contract + lint, feature-flag-off),
`components/account/account.test.tsx` (render smoke: signed out / in / dirty / error / dialogs / Profiles tab / Help).  **Not run here:** the rules against the emulator.

**Rules tests (emulator, needs Java 21+ on your machine):**

```bash
cd deploy/firebase/rules-test
npm install
npm run lint             # offline sanity lint of firestore.rules (no Java needed)
npm run test:emulator    # = npx firebase-tools emulators:exec --only firestore --project demo-msi-rules "npm test"
```

Owner can read / write / delete; another user and the unauthenticated cannot; unknown keys, wrong types, oversize `state`, long names, bad ids, bad settings are rejected.  A test failure here usually means rules and `lib/cloud/store.ts` disagree (the
offline `rulesContract.test.ts` pins the numbers and key lists).

## Mock mode (`npm run dev:mock`)

Serves every class from `src/fixtures/` (no API): schema and defaults are real; the result is the class's fixture result (computed with a Blaze Wizard
companion Lv 10 at the golden case `A140/Chapter Boss/blaze`) scaled by Flat ATTACK, and choosing companion "None" removes the companion's share.  Anything
else you edit (crit, main stat, ...) does NOT move the numbers in mock mode.  A fresh state owns no companion (the schema default is None / level 0): unlock one on the Companions tab first, then pick it on the Calculator.

## Import from Excel (.xlsx)

Profiles tab > **Import from Excel (.xlsx)** (file picker or drag and drop) loads the values a player typed into their own `<Class>/<Class>-DPS-Calculator.xlsx`.  **Privacy: the file is parsed in the browser
(`File.arrayBuffer` -> `fflate` -> `DOMParser`) and never uploaded**; the only request is the class schema (`GET /api/classes/{id}/schema`, or the fixture in mock mode, which therefore works offline).

* **Reader** (`lib/xlsx_read.ts`): opens the zip, reads `xl/workbook.xml` + rels, shared strings and only the worksheets asked for.  Only literal values are used: strings (shared / inline / formula-result), numbers,
  booleans; a formula cell yields its cached `<v>` when present (a workbook generated by our builders and never opened in Excel has none, which is fine: the Inputs cells are literals).  Not SheetJS (`xlsx` on npm is
  unmaintained / vulnerable).  Errors are `XlsxError` with a code and a human message: not a zip, old `.xls` / password-protected (OLE2), not a workbook, macro-enabled (`.xlsm`, `vbaProject.bin`, `.xlsb`), corrupt zip /
  XML, oversize (40 MB), missing sheet.
* **Map** (`lib/xlsx_map.json`): per class id the Inputs title (class detection), header row + content-type names (columns C-L are found by their header text, not position), level / selected-content-type cells (B3 / B4),
  engine key -> Inputs row for every per-content-type input, the 4 artifact slot rows OF THE WORKBOOK (the app / engine allow 5: the workbooks keep 4 rows, so the 5th slot is never imported), the `ArtifactsInput` star column + the (rarity, stat) column pairs of potential lines 1-3 (`lineCols`: C/D, F/G, I/J, checked against the builders) + artifact rows, the `CompanionsInput` level column + companion rows.  Regenerate with
  `python3 web/scripts/gen_xlsx_map.py` from the repository root (system python3, read-only; it imports the builders' layout constants and prints the workbook-only / engine-only key report; `--check` for CI).
  The map also carries the **`PotentialCubes` coordinates per class** (`cubes`: sheet, header / first / last row, the Slot / Potential Type / Rarity / Pity columns and the (stat, value) column pairs of lines 1-3) and a
  top-level **`cubeTables`** (a copy of the engine's cube meta: 15 slots, the two tracks, rarities, stat names, the stats each slot can roll, pity caps, limits; identical for every class).  The generator reads them from the
  builders' constants AND the source of `build_potential_cubes_sheet` (headers list, column writes, sheet name), cross-checks them against the 7 `*.cubes_meta.json` fixtures and (when present) the header row of the committed
  workbooks; any drift is a `PROBLEM` line and `--check` exits 1.
  Today both sides agree on every key: the only engine field without an Inputs row is `companion_level`, which comes from `CompanionsInput`.
* **Mapping** (`lib/importXlsx.ts`, `importWorkbook(book, schema, {classChosen})`): types and applicability come from the schema.  Numbers (also "12.5", "1,234.5", "50 %") are read as numbers; blank / unreadable cells
  fall back to the schema default (unreadable ones with a warning); values outside the schema's min / max, or fractions in whole-number fields, are KEPT as typed and flagged under Warnings; values in cells that do not
  apply to a content type, unknown artifact names, repeated artifacts, unknown headers and formula cells without a saved result are listed under Ignored.  A companion chosen for a content type but "Not unlocked" on
  `CompanionsInput` becomes "None" (warning).  Imported = level, selected content type, every per-content-type value, companion choice per content type, companion levels, the **star level of EVERY artifact** (blank = the workbook's default by rank, "Not Unlocked" = null), the **potential lines** (rarity + stat of lines 1-2, line 3 for Legendary artifacts; stat names are matched to the app's stat keys ignoring case, an unknown stat or rarity is a warning and the line stays empty / Rare) and, **per content type, the equipped artifacts** = the slot rows of that content type's column (slot i of the workbook = slot i of the app, the 5th is left free; an unknown or repeated name is ignored, "(none)" = empty).  The dialog says "equipped artifacts set for N of 10 content types".
  **Cube gear** (`PotentialCubes`, read by NAME: a row is found by its slot + potential type cells, not by position, so a sorted / extended sheet still imports; below the 30-row table only a recognisable pair counts):
  slot (the app's slot id or its label, any case) -> slot id, type (Potential / Bonus Potential), rarity (key or label, any case; unknown -> warning, normal), pity (whole number >= 0; not a number / negative -> warning and 0;
  at or above the track's pity cap, or any pity on the top tier -> warning, KEPT as typed because the engine clamps it), and per line the stat (matched case-insensitively against the cube meta's names; unknown -> warning and
  the line stays empty; **a stat the slot cannot roll is kept and flagged** with a warning, exactly as the Cubes tab flags it in the dropdown) and the value (numbers, numeric text, "%" suffix; a stat with no / bad / negative value ->
  warning, value left empty; a value without a stat -> Ignored).  Only rows that hold something (a rarity above normal, a pity count or a line) are stored, as `FormState.cubes` - the very key the Cubes tab edits and profiles
  save (no second storage); the other rows stay blank.  A class without a Cubes tab yet (no stat values) still gets its gear stored in the profile (the dialog says so).
* **Lossy on purpose**: the computed columns of
  `ArtifactsInput` (DPS gains, Equipped?, ...) and the **Equipment Compare sheet is not imported** (nor CubeData); a Chapter-Stage that Excel turned into a date (`28-9` typed into a General cell) is
  detected only when the serial number is >= 1000 and replaced by the default with a warning.
* **UI** (`components/ImportXlsx.tsx`): a labelled file input (keyboard path) + a drop zone; a modal preview dialog (`role="dialog" aria-modal`, focus moves in / is trapped / Escape closes / focus returns) with the
  detected class (changeable; asked when the title is not one of ours), level, content type, artifacts, companions, **Cubes ("N pieces with lines" + line count + gear rows set)**, values per content type, warnings (grouped by message with their cells) and ignored cells, a
  profile-name field and **Import as new profile** (a name that exists for that class gets " (2)", never overwritten).  The lazy chunk (fflate + map) loads on first use.
* **Tests**: `lib/xlsx_read.test.ts` (reader cases + friendly errors), `lib/importXlsx.test.ts` (per class: a generated workbook per class with sample values at the mapped coordinates vs independently computed
  expectations, map vs schema, the cube gear incl. planted problems and the static cube tables vs the cube-meta fixtures, odd values, missing sheets), `components/ImportXlsx.test.tsx` (render smoke, dialog incl. the Cubes counts, save as new profile).  The `.xlsx` inputs live in `src/test/xlsx/` and are produced by
  `python3 web/scripts/gen_test_xlsx.py` (openpyxl; no real workbook data).  `lib/importXlsx.real.test.ts` imports the real calculators of the repository (`<Dir>/<Class>-DPS-Calculator.xlsx`, found from `web/`) and checks each content type's equipped artifacts against the raw Slot cells; with
  `MSI_REAL_XLSX="$PWD/.." npx vitest run src/lib/importXlsx.real.test.ts --reporter=verbose --silent=false` it also prints what would be imported.

## Regenerating the fixtures

From the repository root (engine output changes -> refresh these so mock mode and the tests keep matching):

```bash
.venv/bin/python web/scripts/gen_fixtures.py --sensitivity-only   # only <id>.sensitivity(.meta).json (classes whose status.stat_values is true) + that flag in classes.json
.venv/bin/python web/scripts/gen_fixtures.py     # every class: schema, defaults, sample inputs, result (through the real API app, TestClient); a class without a workbook golden uses tests/golden/snapshot_common.py::sample_inputs; --out DIR / --class ID for a dry run
.venv/bin/python web/scripts/gen_fixtures.py --artifacts   # only the Artifacts tab data: <id>.artifacts_case.json (classes marked artifacts_modelled in classes.json) + lib/artifact_values.json + lib/artifact_potential_tables.json
.venv/bin/python web/scripts/gen_fixtures.py --cubes-only  # only the cube tabs' fixtures: <id>.cubes_meta / cubes_case / equipment_case / potentials_case .json (classes whose status.stat_values is true; ~7 s)
```

The schema fixtures hold `artifacts.max_slots` = 5 (2026-11-23: the 5th artifact slot; the workbooks keep 4).  Fixtures are regenerated whenever engine output or schema changes; the vitest suite checks they still match the schema logic (the `.result.json` of a class is the API's answer for its sample inputs).
